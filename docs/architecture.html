Персональный маршрут поступления — архитектура и технический план

Команда из двух школьников, 72 часа, разработка с активным использованием AI. Принцип: стабильный простой MVP, который полностью проходит проверочный сценарий жюри, важнее «production-like» архитектуры.

Стек: React + Vite + TS Backend: 1 serverless-эндпоинт Storage: localStorage Deploy: Vercel Гарантия: путь работает без сети

Выбор: Вариант A

Основной путь не зависит от сети и БД → максимальная надёжность демо. Минимум инфраструктуры, вся логика легко тестируется. Один эндпоинт закрывает требование «AI не единственный источник фактов». AI-assisted coding отлично генерирует React + чистый TS.

Trade-off: нет «настоящего» backend и БД — но кейс их не требует: жюри оценивает связный пользовательский путь, а не инфраструктуру.

4. Data model

Основные структуры — UserProfile, University, Program, Deadline, Source, Recommendation, ScoreFactor, RecommendationExplanation, Diagnosis, Roadmap, RoadmapStep. Полные TS-интерфейсы — в docs/ARCHITECTURE.md (§4). Ключевые идеи:

Обязательные поля

Профиль: grade, graduationYear, citizenship, targetCountries, budgetUsdPerYear, needsScholarship, field, gpa. Программа: universityId, field, netTuitionUsdPerYear, requirements, deadlines, sourceIds.

Необязательные поля

examScores, englishLevel, rankingTier, livingCostUsdPerYear, minGpa, languageLevel, dependsOn у шагов.

Источники данных
  • Каждый факт ссылается на sourceId в sources.json.
  • Источник — официальная страница приёмной комиссии, сайт экзамена (IELTS / College Board / НЦТ), страница стипендии.
  • Неподтверждённый факт → isDemo: true + видимый бейдж демо-данные.
  • Правило: никаких выдуманных дедлайнов без бейджа.

5. Recommendation engine

1
User Profile → normalize
Достраиваем пропуски, помечаем отсутствующие поля.
2
Hard filter
Отсекаем заведомо невозможное (цена выше бюджета ×3 без стипендии, недоступный язык).
3
Soft gate по экзамену
Если current/required < 0.8 — программа уходит в «ослабленные», а не в топ.
4
Scoring
7 факторов, взвешенная сумма, breakdown по каждому фактору.
5
Top candidates
Top-5, порог score ≥ 45, детерминированный tie-break.
6
AI explanation → final
Тексты «почему подходит» (или fallback-шаблон), затем финальный список.

Факторы и веса

ФакторВесЧто нормализуется
budget0.25netTuition против бюджета
field0.22совпадение направления
country0.15входит в targetCountries
academic0.15среднее(GPA-fit, exam-fit)
language0.10владение языком обучения
deadline0.08реалистичность успеть
scholarship0.05доступность стипендии

Бюджет + направление = 0.47 вместе — именно они дают заметную реакцию при правке профиля.

Как гарантировать, что изменение профиля что-то меняет
  1. Все 4 «демо-параметра» (страна, бюджет, интерес, экзамен) имеют ненулевой вес.
  2. Страна и интерес меняют порядок; бюджет и экзамен могут менять состав (hard filter и soft gate).
  3. В UI показывается дельта: «после правки бюджета ASU поднялся с 5-го на 3-е место (+25)».
  4. Tie-break детерминированный — без случайности.
  5. Тест sensitivity.test.ts падает, если топ-3 не изменился.

6. AI layer

Принцип: код владеет фактами и решениями, AI владеет формулировками.

Решает код
Решает LLM (опционально)
Фильтрация, скоринг, топ-N, диагностика, roadmap, дедлайны, порядок шагов
«Почему подходит», «чего опасаться», «следующий шаг», переформулировка шагов

POST /api/explain

  • Input: профиль (сокращённый) + рекомендации с breakdown, score, warnings.
  • Output: strict JSON — { items: [{ programId, whyItFits, concerns[], nextStepHint }] }.
  • Fallback: explainFallback.ts собирает текст прямо из breakdown — всегда валиден.
  • Защита от галлюцинаций: только структурированный JSON на входе; programId обязан быть в input; лимит длины строк; temperature 0.2–0.4, timeout 8 s, 1 ретрай; любая ошибка → тихий fallback.

Жёсткое правило: AI никогда не поставляет требования, дедлайны и стоимость. Это только код + JSON + sourceIds.

UI & Flow
