# Кейс №2 «Персональный маршрут поступления» — архитектура и технический план

**Контекст:** LOCUS Startup Hackathon 2026, команда из 2 школьников, 72 часа, разработка с активным использованием AI.
**Главный принцип:** стабильный простой MVP, который на 100% проходит проверочный сценарий жюри, важнее «production-like» архитектуры.

**Продукт в одну фразу:** ученик вводит профиль → проходит короткую диагностику → получает 3+ подходящие программы с объяснением «почему подходит», сравнением, персональным roadmap и одним следующим действием → отмечает прогресс.

---

## 0. Базовые решения (TL;DR)

| Вопрос | Решение |
|---|---|
| Backend | Практически не нужен. Ядро продукта — 100% клиентское |
| Где живёт логика | Чистые TypeScript-функции в браузере (scoring, filter, roadmap) |
| Где живёт AI | Один serverless-эндпоинт `/api/explain`, только для текстов-объяснений |
| Где живёт data | Локальные JSON в репозитории, типизированные TS |
| Где живёт состояние | `localStorage` (профиль + прогресс) |
| Deployment | Vercel (static + 1 serverless function) |
| Гарантия демо | Основной путь работает **без интернета**; AI опционален и имеет fallback |

Главная идея устойчивости: **если AI умрёт, отвалится только «текст-объяснение», всё остальное продолжит работать.** Это осознанный выбор в пользу стабильности.

## 1. Варианты архитектуры

### Вариант A — Offline-first SPA + AI-proxy (рекомендуется)

- **Frontend:** React 18 + TypeScript + Vite, SPA, 7 экранов, mobile-first.
- **Backend:** один serverless-эндпоинт `/api/explain` (Vercel Function) — только вызов LLM, ключ хранится на сервере.
- **Storage:** `localStorage` (профиль, диагноз, статусы шагов). Никакой БД.
- **AI:** один вызов на экране рекомендаций, строгий JSON-выход, детерминированный fallback-шаблон.
- **Data layer:** JSON-файлы в `/src/data` + TS-типы. Скоринг и roadmap — чистые функции в `/src/lib`.
- **Deployment:** Vercel (static build + 1 function). Резерв — GitHub Pages (AI выключен, работает fallback).
- **Сложность:** низкая-средняя.
- **Риски:** ключ LLM, формат JSON от модели, лимиты Vercel на функции (не критично).
- **Что может сломаться за 72 часа:** почти ничего критичного — сеть не участвует в основном пути; максимум «немного некрасивые» объяснения.

### Вариант B — Next.js fullstack (App Router)

- **Frontend:** Next.js 14 + React + TS.
- **Backend:** Route Handlers внутри того же проекта.
- **Storage:** JSON-файлы (или позже Supabase).
- **AI:** server-side вызов.
- **Deployment:** Vercel.
- **Сложность:** средняя.
- **Риски:** server/client components, RSC-ошибки, hydration mismatches, лишние понятия для школьников.
- **Что может сломаться:** «работает локально — падает на билде», путаница `use client`, CORS/кеш.

### Вариант C — SPA + отдельный backend + БД

- **Frontend:** React SPA. **Backend:** Node/Express. **Storage:** Postgres/Supabase. **AI:** server-side.
- **Deployment:** отдельный хостинг backend + фронт.
- **Сложность:** высокая.
- **Риски:** миграции, CORS, деплой двух сервисов, сгоревшее время.
- **Что может сломаться:** всё, что связано с инфраструктурой; кейс этого не требует.

### Сравнение

| Критерий | A (SPA + proxy) | B (Next.js) | C (backend + DB) |
|---|---|---|---|
| Время до первого рабочего экрана | 1–2 ч | 3–5 ч | 8–12 ч |
| Работает без сети | да | частично | нет |
| Безопасность ключа AI | да | да | да |
| Порог для школьника | низкий | средний | высокий |
| Кол-во «движущихся частей» | 1 | 2 | 4 |
| Риск провала демо | низкий | средний | высокий |

**Выбор: Вариант A.** Причины: (1) основной путь не зависит от сети и БД — максимальная надёжность демо; (2) минимум инфраструктуры, вся сложность в чистых функциях, которые легко тестировать; (3) ровно один backend-эндпоинт закрывает требование «AI не должен быть единственным источником фактов»; (4) AI-assisted coding отлично генерирует React + Vite + чистый TS.

Явный trade-off: нет «настоящего» backend-слоя и БД — но кейс их и не требует, а жюри оценивает **связный пользовательский путь**, а не инфраструктуру.

## 2. Минимальный MVP

### MUST HAVE (без этого кейс не засчитан)

1. Landing → вход в продукт (демо-профиль или «продолжить как гость»).
2. Форма профиля: страна, целевые страны, бюджет, направление, класс, экзамены/баллы, средний балл, нужна ли стипендия.
3. Диагностика: 5–8 вопросов, детерминированно считает «сильные стороны / пробелы / рекомендованное направление».
4. Рекомендации: **минимум 3** программы из локальной базы, у каждой — score, разбивка по факторам, бейдж уверенности.
5. «Почему подходит»: 3 причины из breakdown + 1 ограничение (AI или fallback-шаблон).
6. Сравнение **минимум 2** программ по таблице критериев.
7. Roadmap: экзамены, документы, дедлайны, академические шаги, активности.
8. Одно выделенное **следующее действие** (детерминированное правило).
9. Отметка прогресса шага → прогресс-бар и пересчёт «следующего действия».
10. Mobile-first верстка, единая дизайн-система (токены + компоненты).
11. Изменение страны / бюджета / интереса / экзамена **заметно** меняет рекомендации и/или roadmap.
12. Источники у фактов: поле `sourceIds` у университетов/программ/дедлайнов + явный бейдж «демо-данные» там, где источник не подтверждён.

### SHOULD HAVE

- Сохранение профиля и прогресса в `localStorage` между перезагрузками.
- Empty state и `error`-состояния на всех экранах + скелетоны загрузки.
- Панель «не нашлось идеального варианта» с конкретными подсказками по ослаблению фильтров.
- Экспорт roadmap в печатную версию (браузерный `print()`).
- Дисклеймер о демонстрационных данных на экране источников.

### NICE TO HAVE

- Второй AI-вызов: переписывание шагов roadmap «человеческим» языком.
- Несколько полей направления (major + minor).
- Мягкий режим «показать всё, игнорируя одну группу фильтров».
- Тёмная тема (только если дизайн-токены готовы заранее).

### НЕ ДЕЛАТЬ

- Реальную авторизацию/OAuth, пароли, роли (вход = демо-профиль).
- БД, ORM, миграции, микросервисы, Docker.
- AI-чат как интерфейс продукта.
- Каталог университетов «просто список с поиском».
- Парсинг сайтов вузов на лету, вебхуки, фоновые джобы.
- Админку, аналитику, платежи, push-уведомления, мультиязычность.
- SSR/SSG-сложности и любые оптимизации до прохождения демо-сценария.

## 4. Data model (TypeScript)

> Легенда: `?` — необязательное поле. Все обязательные поля должны быть заполнены во всех записях базы.

```ts
export type CountryCode = 'KZ' | 'RU' | 'US' | 'UK' | 'DE' | 'IT' | 'CA' | 'TR' | 'KR';
export type Field = 'cs' | 'engineering' | 'business' | 'medicine' | 'humanities' | 'design';
export type ExamId = 'IELTS' | 'TOEFL' | 'SAT' | 'ENT' | 'DUOLINGO';
export type Fit = 'high' | 'medium' | 'low';
export type Confidence = 'high' | 'medium' | 'low';
export type StepPhase = 'exams' | 'documents' | 'deadlines' | 'academic' | 'activities';
export type StepStatus = 'todo' | 'in_progress' | 'done';
```

```ts
export interface UserProfile {
  id: string;                       // генерируется на клиенте
  name?: string;                     // необязательно
  grade: 9 | 10 | 11;                // обязательное
  graduationYear: number;            // обязательное
  citizenship: CountryCode;          // обязательное
  targetCountries: CountryCode[];    // обязательное, ≥1
  budgetUsdPerYear: number;          // обязательное (бюджет на обучение)
  needsScholarship: boolean;         // обязательное
  field: Field;                      // обязательное
  examScores: Partial<Record<ExamId, number>>; // может быть пустым
  gpa: number;                       // 0..5, обязательное
  englishLevel?: 'A2' | 'B1' | 'B2' | 'C1';    // необязательно
  createdAt: string;                 // ISO
  updatedAt: string;                 // ISO
}
```

```ts
export interface University {
  id: string;                        // обязательное
  name: string;                      // обязательное
  country: CountryCode;              // обязательное
  city: string;                      // обязательное
  type: 'public' | 'private';        // обязательное
  website: string;                   // обязательное
  rankingTier?: 1 | 2 | 3;           // необязательно (демо-ориентир)
  livingCostUsdPerYear?: number;     // необязательно (инфо, не в scoring)
  scholarshipAvailable: boolean;     // обязательное
  scholarshipNote?: string;          // необязательно
  languagesOfInstruction: string[];  // обязательное
  sourceIds: string[];               // обязательное, ≥1
}

export interface Program {
  id: string;                        // обязательное
  universityId: string;              // обязательное (FK → University.id)
  name: string;                      // обязательное
  field: Field;                      // обязательное
  degree: 'bachelor';                // обязательное (MVP: только бакалавриат)
  durationYears: number;             // обязательное
  netTuitionUsdPerYear: number;      // обязательное (после типовой стипендии)
  languagesOfInstruction: string[];  // обязательное
  requirements: {
    exams: { exam: ExamId; minScore: number }[]; // может быть []
    minGpa?: number;                              // необязательно
    languageLevel?: string;                       // необязательно
  };
  deadlines: Deadline[];             // обязательное, может быть []
  sourceIds: string[];               // обязательное, ≥1
}

export interface Deadline {
  id: string;                        // обязательное
  kind: 'application' | 'documents' | 'exam' | 'scholarship' | 'visa';
  date: string;                      // ISO, обязательное
  label: string;                     // обязательное
  programId?: string;                // необязательно
  sourceId?: string;                 // необязательно
  isDemo: boolean;                   // обязательное: true = демо-дата
}

export interface Source {
  id: string;                        // обязательное
  title: string;                     // обязательное
  url: string;                       // обязательное
  kind: 'official' | 'demo';         // обязательное
  note?: string;                     // необязательно
  accessedAt?: string;               // необязательно (ISO)
}

export interface Recommendation {
  programId: string;                 // обязательное
  universityId: string;              // обязательное
  score: number;                     // 0..100
  fit: Fit;                          // обязательное
  confidence: Confidence;            // по доле доступных факторов
  breakdown: ScoreFactor[];          // обязательное, ≥1
  warnings: string[];                // обязательное, может быть []
  sourceIds: string[];               // обязательное
  explanation?: RecommendationExplanation; // заполняется после AI/fallback
}

export interface ScoreFactor {
  key: 'budget' | 'field' | 'country' | 'academic' | 'language' | 'deadline' | 'scholarship';
  label: string;
  weight: number;                    // исходный вес (0..1)
  effectiveWeight: number;           // вес после перераспределения
  normalized: number;                // 0..1
  contribution: number;              // effectiveWeight * normalized * 100
}

export interface RecommendationExplanation {
  whyItFits: string;                 // 1–3 предложения
  concerns: string[];                // 0–3 пункта
  nextStepHint: string;              // одно действие
  origin: 'ai' | 'fallback';         // ВАЖНО для честности на защите
}

export interface Diagnosis {
  id: string;                        // обязательное
  completedAt: string;               // ISO
  answers: Record<string, string | number | boolean>; // ответы по question.id
  derived: {
    strengths: string[];             // 2–4
    gaps: string[];                  // 0–4
    recommendedField?: Field;        // необязательно
    recommendedCountries?: CountryCode[];
  };
  missingProfileFields: string[];    // какие поля профиля пустые
}

export interface Roadmap {
  id: string;
  profileId: string;
  programIds: string[];              // на какие программы построен
  createdAt: string;
  items: RoadmapStep[];
  nextActionId: string;              // вычисляется, не хранится вручную
}

export interface RoadmapStep {
  id: string;
  phase: StepPhase;                  // обязательное
  title: string;                     // обязательное
  description: string;               // обязательное
  dueDate?: string;                  // ISO, необязательно
  status: StepStatus;                // обязательное
  priority: 1 | 2 | 3;               // 1 = выше
  dependsOn?: string[];              // id шагов-предшественников
  linkedProgramId?: string;          // необязательно
  sourceIds: string[];               // обязательное, может быть []
}
```

### Источники данных — как это устроено

1. Каждый факт (требование, дедлайн, стоимость) ссылается на `sourceId`.
2. `sources.json` содержит: официальные страницы приёмных комиссий, сайты экзаменов (IELTS/College Board/НЦТ), страницы стипендий (напр. Bolashak), либо запись `kind: "demo"`.
3. Если факт не подтверждён официальным источником — `isDemo: true` и в UI виден бейдж <kbd>демо-данные</kbd>.
4. Правило команды: **никаких выдуманных дедлайнов без бейджа**. См. `docs/DATA_SOURCES.md`.

## 5. Recommendation engine

Конвейер (жёстко зафиксированный):

```
UserProfile
  → normalize (достроить пропуски)
  → hard filter (отсечь заведомо невозможное)
  → soft gate (отсечь недостижимое по экзамену)
  → scoring (7 факторов, взвешенная сумма)
  → top candidates (top N = 5, порог score ≥ 45)
  → AI explanation (или fallback)
  → final recommendations
```

### Факторы и веса

| Фактор | Вес | Что нормализуется |
|---|---|---|
| `budget` | **0.25** | `netTuition` против бюджета |
| `field` | **0.22** | совпадение направления программы и профиля |
| `country` | **0.15** | входит ли страна вуза в `targetCountries` |
| `academic` | **0.15** | среднее из (соответствие GPA) и (соответствие экзаменам) |
| `language` | **0.10** | владение языком обучения (английский/немецкий) |
| `deadline` | **0.08** | реалистичность успеть к дедлайну из текущего класса |
| `scholarship` | **0.05** | доступность стипендии/низкая цена |

Сумма весов = 1.00. **Бюджет и направление — доминирующие** (0.47 вместе): именно они дают заметные изменения при правке профиля.

### Формулы нормализации

```
budget:      netTuition <= budget  → 1.0
             иначе                 → max(0, 1 - (netTuition - budget) / budget)

field:       program.field === profile.field  → 1.0
             смежные направления              → 0.5
             иначе                            → 0.0

country:     country ∈ targetCountries → 1.0, иначе 0.0

academic:    gpaFit  = profile.gpa >= minGpa ? 1.0 : profile.gpa / minGpa
             examFit = для каждого required exam:
                       current >= min          → 1.0
                       иначе                   → 0.5 * (current / min)   // штраф за пробел
             academic = mean(gpaFit, examFits…)

language:    язык программы доступен и подтверждён → 1.0 / 0.9 / 0.4 по уверенности

deadline:    успеваю по срокам        → 0.9–1.0
             впритык                  → 0.6–0.8
             не успеваю               → 0.2–0.4

scholarship: есть стипендия / низкая цена → 0.7–1.0
             нет                       → 0.2–0.4
```

### Итоговый score

```
score = Σ (effectiveWeight_f × normalized_f) × 100
```

`fit`: ≥75 → high, 55–74 → medium, 45–54 → low.
**Уверенность (confidence):** доля доступных факторов. Если сумма исходных весов заполненных факторов < 0.6 → `low`, 0.6–0.85 → `medium`, > 0.85 → `high`. При пропуске фактора его вес **перераспределяется** пропорционально между остальными.

### Жёсткие фильтры и soft-gate

- **Hard filter:** программа исключается, если `netTuition > budget × 3` и стипендии нет; либо язык обучения не изучался и не заявлен.
- **Soft gate по экзамену:** если `current / required < 0.8`, программа помечается «недостижимо сейчас» и уходит в блок «ослабленные варианты», а не в топ.
- **Ни country, ни field не являются hard-фильтрами** — иначе изменение страны/интереса просто «обнуляет» список. Они остаются soft-факторами, чтобы список **переупорядочивался**, а не исчезал.

### Как гарантировать, что изменение профиля что-то меняет

1. Четыре «демо-параметра» (страна, бюджет, интерес, экзамен) все входят в score с ненулевым весом.
2. Страна и интерес меняют **порядок**, бюджет и экзамен могут менять **состав** списка (через hard filter и soft gate).
3. В UI показывается дельта: «после изменения бюджета ASU поднялся с 5-го на 3-е место (+25 баллов)».
4. Tie-break — детерминированный (по score, затем по названию), без случайности.
5. Регрессионный тест `sensitivity.test.ts` падает, если после смены параметра топ-3 не изменился.

### Что делать, если подходящих вариантов нет

1. Показать честный empty state: «Идеального совпадения нет».
2. Сгенерировать **ослабленные варианты** алгоритмически: игнорировать по одному фактору (сначала стипендию, потом бюджет ×1.5, потом страну) и показать ближайшие 3.
3. Для каждого — конкретная подсказка: «Нужно +$4 000/год» или «Добавь Германию — там 2 подходящие программы».

## 6. AI layer

Принцип: **код владеет фактами и решениями, AI владеет формулировками.**

| Задача | Кто решает | Почему |
|---|---|---|
| Фильтрация, скоринг, топ-N | **код** | детерминизм, объяснимость жюри |
| Дедлайны, требования, цены | **данные (JSON)** | нельзя давать LLM придумывать факты |
| Диагностика → выводы | **код** | предсказуемость |
| Roadmap (шаги, даты, порядок) | **код** | нужны реальные дедлайны из данных |
| «Почему подходит» / «чего опасаться» | **LLM (опц.)** | естественный язык |
| Тон/мотивация в шагах | **LLM (NICE)** | не критично |

### Единственный обязательный AI-вызов: `POST /api/explain`

- **Input:** `{ profile: {grade, field, targetCountries, budgetUsdPerYear, examScores}, recommendations: [{programId, universityName, programName, netTuitionUsdPerYear, score, fit, warnings, breakdown: [{key,label,normalized,weight}]}] }`
- **Output (strict JSON):**
```json
{
  "items": [
    {
      "programId": "string (обязательно, из input)",
      "whyItFits": "1–3 предложения, без новых чисел",
      "concerns": ["строка", "строка"],
      "nextStepHint": "одно конкретное действие"
    }
  ]
}
```
- **Зачем AI:** превратить сухую таблицу факторов в живое объяснение, которое жюри видит как «персонализацию».
- **Fallback:** `explainFallback.ts` собирает текст из breakdown: *«Программа подходит на 91%: сильнее всего сыграли направление (22%) и бюджет (25%). Ограничение — английский: требуется IELTS 6.5, у тебя 6.0.»* Fallback всегда даёт валидный результат.
- **Защита от галлюцинаций:**
  1. LLM получает **только** структурированный JSON и не имеет права вводить новые числа/факты.
  2. Ответ валидируется: каждый `programId` обязан быть в input, иначе — отбрасываем и берём fallback для этого элемента.
  3. Строки ограничены по длине (≤400 символов), лишнее обрезается.
  4. `temperature: 0.2–0.4`, `max_tokens` ограничен, `timeout: 8 s`, максимум **1** ретрай.
  5. Любая ошибка (сеть/429/невалидный JSON/таймаут) → тихий переход на fallback, UI показывает бейдж источника объяснения.

### Опциональный вызов (SHOULD/NICE): `POST /api/rewrite-steps`

- **Input:** `{ steps: [{id, phase, title, description}] }`
- **Output:** `{ items: [{id, title, description}] }`
- **Зачем:** сделать roadmap «человечнее».
- **Fallback:** исходные формулировки.
- **Риск:** низкий, но включаем только если остаётся время.

**Жёсткое правило:** AI никогда не поставляет требования, дедлайны и стоимость. Это только код + JSON + `sourceIds`.

## 7. Пользовательский flow

```
Landing → Profile → Diagnosis → Recommendations → Comparison → Roadmap → Next Action
                     ↑_________________ отметка прогресса ______________|
```

| Экран | Цель | Вход | Действия | Выход | Loading | Error | Empty |
|---|---|---|---|---|---|---|---|
| **Landing** | Объяснить продукт и завести в путь | — | «Начать», «Продолжить» (если есть сохранённый профиль) | Переход на Profile | — | — | Кнопки «Продолжить» нет, если профиля нет |
| **Profile** | Собрать ключевые параметры | Черновик профиля | Заполнить форму, «Далее» | `UserProfile` в store + localStorage | Инлайн-валидация | Подсветка полей, текст ошибки | Подсказка «Заполни 6 полей» |
| **Diagnosis** | Уточнить сильные стороны/пробелы | `UserProfile` | Ответить на 5–8 вопросов | `Diagnosis` (deterministic) | Скелетон вопросов | «Не удалось посчитать — повторить» | Кнопка «Пропустить диагностику» |
| **Recommendations** | Дать 3+ варианта с «почему» | `UserProfile` + `Diagnosis` | Открыть карточку, добавить в сравнение | `Recommendation[]` с explanation | Скелетон карточек + бейдж «подбираем объяснения» | «AI недоступен — показаны шаблонные объяснения» | Панель «идеального совпадения нет» + ослабленные варианты |
| **Comparison** | Сравнить ≥2 программы | 2–3 выбранные программы | Убрать/добавить, сменить критерий | Таблица сравнения | Скелетон таблицы | — | «Выбери минимум 2 программы» |
| **Roadmap** | Дать план по шагам | Выбранные программы + пробелы профиля | Отмечать шаги, раскрывать детали | `Roadmap` с `nextActionId` | Скелетон таймлайна | «Не удалось сохранить — повторить» | «Сначала получи рекомендации» |
| **Next Action** | Одно понятное действие | `Roadmap` | «Готово» / «Отложить» | Обновлённый прогресс | — | — | — |
| **Sources** | Честность по фактам | `sources.json` | Открыть ссылку | — | — | — | «Все данные демонстрационные» |

**Прогресс** живёт на Roadmap: `done / total` + пересчёт `nextActionId` по правилу «первый невыполненный шаг с минимальным (priority, dueDate)».

## 8. API / service boundaries

**Можно ли обойтись без backend?** Для ядра — да: профиль, диагностика, скоринг, roadmap, прогресс считаются на клиенте. Backend нужен **ровно для одного** — спрятать ключ LLM и не светить его в бандле.

Поэтому минимальный набор:

| Метод | Endpoint | Зачем | Обязателен |
|---|---|---|---|
| POST | `/api/explain` | AI-объяснения рекомендаций | Опционально (есть fallback) |
| POST | `/api/rewrite-steps` | Переформулировка шагов roadmap | Нет |
| GET | `/api/health` | Проверка живости AI (для демо) | Нет |

Правила:
- Никаких endpoint'ов «на будущее».
- Скоринг и roadmap **не выносим** на сервер: перенос увеличит число точек отказа.
- Если деплой статический (GitHub Pages) — `/api/*` просто не используется, и продукт остаётся рабочим.

## 10. Демо для жюри (2–3 минуты)

Идея: **никакой захардкоженной персонализации** — все результаты считаются вживую, и жюри видит реакцию системы на правку профиля.

1. **0:00–0:15 — Landing.** Одна фраза: «Мы собираем персональный маршрут поступления за 2 минуты».
2. **0:15–0:45 — Profile + Diagnosis.** Заполняем профиль (Алия: KZ, `cs`, бюджет $6 000, IELTS 6.0) и быстро проходим диагностику.
3. **0:45–1:15 — Recommendations.** Появляются 3+ программы с score и разбивкой. Открываем «почему подходит» (AI-текст или fallback — в углу виден бейдж источника).
4. **1:15–1:40 — Живое изменение.** Меняем целевые страны на `[US, CA]` и бюджет на $30 000 → ASU подскакивает в топ. Это ключевой момент: **жюри видит, что персонализация настоящая**.
5. **1:40–2:10 — Comparison.** Сравниваем 2 программы по таблице (цена, требования, дедлайны, язык).
6. **2:10–2:40 — Roadmap + прогресс.** Открываем маршрут, отмечаем первый шаг «done», прогресс-бар двигается, «следующее действие» переключается на следующий шаг.
7. **2:40–3:00 — Sources.** Показываем, что дедлайны имеют источники, а неподтверждённое честно помечено как «демо-данные».

Подстраховка: всё, кроме п.3, работает без интернета. Если AI лёг — показываем fallback-объяснения и говорим об этом прямо (это плюс, а не минус).

## 14. Definition of Done

| Функция | Критерий «готово» |
|---|---|
| Профиль | Все обязательные поля валидируются; профиль сохраняется и восстанавливается после перезагрузки |
| Диагностика | 5–8 вопросов; результат детерминирован (одинаковые ответы → одинаковый вывод) |
| Рекомендации | ≥3 программы с score и breakdown; каждая объяснима через веса |
| «Почему подходит» | Есть текст-причина и ≥1 ограничение; указан источник объяснения (AI/fallback) |
| Сравнение | ≥2 программы в таблице; все критерии берутся из данных |
| Roadmap | Покрыты все 5 фаз (экзамены/документы/дедлайны/академические/активности) |
| Следующее действие | Ровно одно выделено; пересчитывается при отметке шага |
| Прогресс | Статус шага сохраняется; прогресс-бар обновляется сразу |
| Чувствительность | Смена страны/бюджета/интереса/экзамена меняет рекомендации или roadmap (тест зелёный) |
| Источники | У каждого факта есть `sourceId` или бейдж «демо-данные» |
| Мобильная версия | Путь проходит на ширине 360 px без горизонтального скролла |
| Деплой | Публичный URL открывается на телефоне; fallback работает при выключенном AI |

## 15. Итоговая сводка

**A. Recommended architecture** — Offline-first React + Vite SPA; вся логика в чистых TS-функциях; один serverless-эндпоинт `/api/explain` для AI; `localStorage` вместо БД; Vercel для деплоя.

**B. Recommended stack** — React 18, TypeScript (strict), Vite, Tailwind CSS + собственные дизайн-токены, react-router-dom, Context + useReducer, Vitest, Vercel Functions.

**C. Project tree** — см. §3.

**D. Data model** — см. §4: `UserProfile`, `University`, `Program`, `Deadline`, `Source`, `Recommendation`, `ScoreFactor`, `RecommendationExplanation`, `Diagnosis`, `Roadmap`, `RoadmapStep`.

**E. Recommendation algorithm** — hard filter → soft gate → 7-факторный взвешенный scoring (budget 0.25, field 0.22, country 0.15, academic 0.15, language 0.10, deadline 0.08, scholarship 0.05) → top-5 → AI/fallback explanation; перераспределение весов при пропусках; ослабленные варианты при отсутствии совпадений.

**F. AI responsibilities** — только формулировки «почему подходит», «чего опасаться», «следующий шаг» (+ опционально переписывание шагов). Никогда не источник фактов. Всегда есть fallback.

**G. API/service structure** — `POST /api/explain` (опц.), `POST /api/rewrite-steps` (не обяз.), `GET /api/health` (не обяз.). Ядро работает без backend.

**H. Team split** — A: данные, скоринг, roadmap, AI-эндпоинт, тесты. B: дизайн-система, экраны, состояние, mobile, демо. Контракт — `types.ts`.

**I. Development order** — Phase 0…9 последовательно: архитектура → скелет → данные → логика → UI → AI → интеграция → тесты → деплой → демо.

**J. Testing plan** — 5 профилей + sensitivity-тесты на страну/бюджет/интерес/экзамен + ручной mobile-чек-лист.

**K. Demo scenario** — 2–3 минуты с живым изменением профиля в середине; подстраховка на fallback-объяснениях.

**L. Biggest risks** — невалидный JSON от LLM, отсутствие подходящих программ, mobile layout, деплой в последний час; все закрыты fallback'ами и ранним деплоем.

**M. What NOT to build** — авторизация, БД, микросервисы, AI-чат, каталог, парсинг на лету, админка, платежи, push, мультиязычность.
